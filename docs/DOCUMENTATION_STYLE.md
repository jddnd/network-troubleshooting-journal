# Documentation Style

The journal uses **Markdown for the case narrative, YAML frontmatter for structured metadata, and generated HTML for the website**.

Do not hand-author HTML for troubleshooting cases. Markdown remains the source of truth in GitHub; the website renderer turns it into HTML.

## Core classification model

Every case should answer three questions before the investigation narrative begins:

1. **Discipline** — what engineering domain owns the problem?
2. **Platform** — what system or product is being investigated?
3. **Aspect** — what behavior, subsystem, or capability of that platform is under investigation?

These are deliberately separate.

### Discipline

The top-level engineering domain:

- Routing
- Switching
- Firewall
- Wireless
- Identity
- PKI

A case has one primary discipline. Other domains encountered during fault isolation can be recorded as secondary disciplines.

### Platform

The implementation being investigated. Capture the vendor, product family, and relevant components without making the vendor the organizing principle of the journal.

Example:

```yaml
primary_platform:
  vendor: Cisco
  family: Catalyst 9800
  components:
    - C9800-CL
    - CW9176I
```

Supporting platforms can be listed separately when the investigation crosses systems, for example Cisco ISE in a wireless case.

### Aspect

The specific behavior, subsystem, or capability under investigation.

Examples:

- Routing → Cisco IOS-XE → BGP path selection
- Routing → Cisco SD-WAN → overlay route propagation
- Switching → Catalyst 9300 → STP convergence
- Firewall → FortiGate → IPsec tunnel establishment
- Wireless → Catalyst 9800 → client roaming
- Identity → Cisco ISE → RADIUS authorization
- PKI → Microsoft AD CS → certificate issuance

The aspect should be more precise than a broad product area such as `wireless` or `routing`, but broader than an individual command or log message.

## Mechanisms

Mechanisms describe the protocols, standards, algorithms, or features involved in the aspect. They are useful for search and cross-linking, but they do not replace the primary aspect.

Examples:

- 802.11r
- 802.11k
- 802.11v
- RRM
- TPC
- EAP-TLS
- BGP
- OSPF
- IPsec
- STP
- RADIUS
- OCSP

## Symptoms

Symptoms record what triggered the investigation before a cause was known.

Examples:

- Teams call interruptions
- intermittent packet loss
- route not installed
- IPsec tunnel flapping
- 802.1X authentication rejected
- certificate chain validation failure

Symptoms should not contain an assumed root cause.

## Recommended frontmatter

```yaml
---
title: "Case title"
case_id: "000"
status: "investigating"

discipline: "wireless"
secondary_disciplines:
  - identity
  - pki

primary_platform:
  vendor: "Cisco"
  family: "Catalyst 9800"
  components:
    - "C9800-CL"
    - "CW9176I"

supporting_platforms:
  - vendor: "Cisco"
    family: "Identity Services Engine"
    components:
      - "Cisco ISE"

aspect:
  primary: "client-roaming"
  secondary:
    - "rf-cell-sizing"
    - "rrm-tpc"
    - "fast-transition"

mechanisms:
  - "802.11r"
  - "802.11k"
  - "802.11v"
  - "WPA3-Enterprise"
  - "802.1X"
  - "EAP-TLS"

symptoms:
  - "Teams call interruptions"
  - "perceived Wi-Fi disconnects"

first_observed: "YYYY-MM-DD"
last_updated: "YYYY-MM-DD"
public_ready: false
---
```

## Narrative structure

After the frontmatter, each case should tell the engineering story in roughly this order:

1. Case classification
2. Problem statement
3. Environment
4. Impact
5. Fault domains
6. Timeline
7. Evidence
8. Hypotheses
9. Controlled experiments
10. Root cause
11. Resolution
12. Verification
13. What was ruled out
14. Engineering lessons
15. Follow-up

The important pattern is:

**Observation → hypothesis → evidence → falsification → controlled experiment → verification → conclusion.**

## Classification rule

Classify by the **engineering behavior being investigated**, not by the vendor appliance implementing it.

For example, SD-WAN is primarily a Routing aspect even when a firewall platform provides the implementation. A FortiGate SD-WAN case can therefore be primarily Routing with Firewall as a secondary discipline.

Likewise, a Wireless case that uses Cisco ISE and EAP-TLS during fault isolation remains primarily Wireless when the behavior under investigation is client roaming.

## Why Markdown + YAML

- **Markdown** is easy to read and review directly in GitHub and is ideal for the investigation narrative.
- **YAML frontmatter** gives the website structured fields for filtering, search, badges, case cards, and navigation.
- **HTML** should be generated by the site framework from the Markdown rather than maintained manually.

This keeps GitHub as the durable source of truth while still allowing a richer website later.
